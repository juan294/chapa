# High-volume badge collection implementation notes

Implementation branch: `fix/high-volume-badge-collection`, based on `26648ab9d48fa483cee2f6a05b5d12bb261d2dbd`.

## Deviations

### Phase 1: checkpoint fails before the old 50,000-event cap

- **Plan said:** The current 50,000-event path would stage all rows, and the 100,000-event fixture would demonstrate the existing `event_limit` boundary.
- **Found:** A synthetic 17,572-event job staged successfully but `scoring_collection_finish` reached the configured 8-second statement timeout on the loaded local stack. A separate 50,000-event job timed out during a 2,000-event checkpoint after 18,000 rows were staged. On a lean local stack, 17,572 events completed and issued a receipt, while 50,000 events staged but the database backend running finish was killed by signal 9 (HTTP 503). The 100,000-event case reached the old `event_limit` after staging 52,000 rows. The checkpoint SQL scans the growing staged set to count it after each insert.
- **Chose:** Treat bounded checkpoint latency and failure atomicity as explicit Phase 2 acceptance gates. Keep the old cap until every read, scoring, and recovery gate passes. Record the 100,000-event baseline as the earliest actual boundary, which may be the checkpoint timeout rather than `event_limit`.
- **Why:** Raising the cap or changing finish alone cannot complete a larger account reliably if later checkpoints or the single large finish overload the database. The loaded and lean results show latency is not determined by event count alone.

### Phase 1: timing interpretation

- **Plan said:** Attribute a share of the finish time to each SQL step.
- **Found:** Separate local rollback profiles measure stand-alone operations but do not add to the duration of the single `scoring_collection_finish` transaction. On the loaded stack, the 17,572-event profile measured count 4.04 ms, ordered aggregation 379.082 ms, source validation 5,960.351 ms, observation insert 343.142 ms, and staged deletion 64.545 ms. Source validation fell to 1,514 ms on the lean stack. The full finish timed out on the loaded stack but succeeded in 2,571 ms on the lean stack.
- **Chose:** Report those as isolated stage measurements, not percentages of the production statement. Profile checkpoint operations separately as the newly observed boundary.
- **Why:** Setup, PL/pgSQL call overhead, source authorization, locks, and returning the full payload are outside those isolated measurements.

### Phase 1: backend termination at 50,000 events

- **Plan said:** The existing 50,000-event bound would be measured as a finish/read baseline, and Phase 2 would remove the aggregate/copy/delete work from finish.
- **Found:** The lean-stack 50,000-event finish returned HTTP 503 after 10,706 ms. The local PostgreSQL log records the finish backend terminated by signal 9, followed by database recovery. The log does not identify the signal sender or prove an out-of-memory cause.
- **Chose:** Treat database process survival, not just statement latency, as a Phase 2 acceptance condition. Do not rerun the old 50,000-event finish solely to force it through. Continue with immutable event rows and small finish metadata, since that design removes the large in-transaction aggregate, validation loop, JSONB copy, delete, and response.
- **Why:** A timeout-only fix would leave the database process failure and the 31 MB response observed even at 17,572 events.

### Phase 2: migration filename convention

- **Plan said:** Create the migration with `supabase migration new` after `060`.
- **Found:** The CLI generated a timestamp name, but this repository's migration validator and runbook require contiguous three-digit names. The full unit suite caught the mismatch.
- **Chose:** Keep the generated SQL and rename it `061_collection_event_generations.sql`. Reset the disposable local database from zero with that exact file and run `pnpm run validate:migrations`.
- **Why:** The release and CI migration gates use the repository convention; a timestamp file would fail before deployment.

### Phase 2: checkpoint size under suite load

- **Plan said:** Bound checkpoint writes below the eight-second statement timeout without moving the 50,000-event cap.
- **Found:** Two-thousand-event checkpoints passed the focused queue suite but one timed out during the full default-concurrency contract suite after a 50,000-event generation had already been published. The backend stayed available. The old 50,000-event finish failure did not recur.
- **Chose:** Cap worker checkpoint calls at 1,000 events, keep the durable cursor and progress unchanged until the final batch, and time every 1,000-event call in both first and refresh generations. Keep legacy import pages at 2,000; the 17,572-row import passed under default contract-suite load.
- **Why:** The default suite reproduces the loaded condition and matches CI's contract runner. A focused pass alone cannot establish the latency gate.

### Phase 3: coordinator compatibility during the read transition

- **Plan said:** Move source selection and issuance to manifests and pages in Phase 3, with no full source array.
- **Found:** The existing source coordinator returns a `StoredSourceObservation` containing an event array, and the scoring consumer uses that shape. Changing only the coordinator in Phase 3 would require the Phase 4 reducer and digest change before issuance could consume pages.
- **Chose:** Route `readSourceObservation` through the new manifest and verified page iterator as a temporary compatibility adapter. The database response and prior-day seed are bounded, and issuance sees an observation only after all pages pass validation. The coordinator still materializes up to the current 50,000-event cap in memory. Removing that array remains a Phase 4 acceptance gate; Phase 3 does not claim bounded issuance memory or 100,000-event issuance.
- **Why:** This preserves the existing receipt path while the page/storage boundary and the reducer are qualified sequentially. The 100,000-event cap stays closed until Phase 4 and Phase 5 pass.

### Phase 3: serialize scale contracts on the shared local stack

- **Plan said:** Run the full local contract suite after focused 50,000- and 100,000-event page and seed checks.
- **Found:** The first unfiltered run placed a direct 100,000-row INSERT alongside a 50,000-row prior seed and the older 12,000/50,000-row queue contracts. PostgreSQL logged the 100,000-row INSERT at 81.9 seconds; two cleanup hooks exceeded their 10-second test limit, and the 12,000-row read failed with a generic adapter error. The database logged no statement timeout, deadlock, OOM, or restart; the underlying read error was not exposed. The 12,000-row read and 50,000-row seed both passed in a focused pair.
- **Chose:** Keep the small page/authorization contracts in the default concurrent suite and run the new 50,000/100,000 scale cases under `SCORING_RUN_SCALE_CONTRACT=1` as a separate serialized local gate. Repeat the default suite after this split. The phase is not accepted until both default and scale runs pass.
- **Why:** Concurrent fixture insertion saturated the shared local PostgREST pool and made the result depend on unrelated test scheduling. Separate qualification preserves the large behavior check and a meaningful default-suite load test.

## Phase 3 handoff

- **Scope and state:** Local Phase 3 on `fix/high-volume-badge-collection`; migration `062_paged_source_reads.sql` is applied only to the task-owned disposable stack. - **Read and seed contract:** Service-only manifest and keyset-page RPCs recheck source and current link authority on every call. A selected row generation is read in pages of at most 500, in UTF-8 byte order. The client checks each event key, strict ordering, count, and SHA-256 digest before completing the iterator. Legacy JSONB observations retain their validated reader and emit bounded pages. The worker seeds a prior observation page by page, stages at most 1,000 events per checkpoint, and uses the database's distinct staged count; a failed page leaves the cursor replayable. Repeated seed storage faults and deadline expiry use lease-fenced, bounded retries and become terminal/action-needed after three attempts. Until Phase 5 adds a dedicated storage diagnostic, `prior_source_storage` is recorded under the existing `protocol` stop kind.
