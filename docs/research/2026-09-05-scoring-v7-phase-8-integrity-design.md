# Scoring v7: source integrity implementation design

S08 / #1303. Prepared by GPT-6 Astra and accepted by the integration owner as the implementation direction. This is a design record, not a completion claim. S14 is locally integrated at `95190436`; S04's issue-API amendment remains pending user approval.

Implementation is divided into three bounded parts in the same isolated integrity worktree. The combined task still requires independent review and all local gates before closure. Part A's live guard changes are disjoint from S14 and began while S14's final integration gates ran; the integrity worktree was then fast-forwarded to S14 before its checks.

## A: Retire productivity-based rejection

Delivery style, zero PRs, annual expiration, low changed-line counts, PR weights and public/authenticated labels cannot establish corruption. Replace these live rejection paths in the GitHub client, raw-stat collector and legacy materialization boundary. Retain structural rejection of malformed fields and invalid numeric domains. Existing scalar StatsData remains legacy v6 data; structural validity is not evidence of complete v7 coverage. Preserve concurrency, source-failure and overlay regressions while replacing assertions that encode the audited mistakes.

## B: Bind source selection to actual access context

Use one server-only source coordinator with owner, source identity, exact reference/window, declared scope, internally constructed credential binding and read-only/refresh mode. The binding uses the effective credential actually passed to the collector, including GitHub server-token fallback and refreshed linked tokens. Combine a private keyed fingerprint with provider/host and current linked-row identity/version; an arbitrary caller label or public/authenticated rank is insufficient. Tokens and fingerprints never enter public receipts, outputs or logs.

The private access binding uses the requested provider/host/login, current link identity/version, effective credential and declared scope. It stays stable across reference times so older compatible observations can be found. A separate selection ID adds the exact window/reference for in-flight work. Requested login is never substituted for the canonical provider subject ID in normalized evidence. An authorized stored-source discovery read returns one canonical identity for the exact binding, an explicit miss, or ambiguity; it never fetches provider identity on a read-only path or guesses among multiple subjects.

Current flags and link records are checked before lookup and after asynchronous work. A strict linked-record lookup must distinguish no link from storage/decryption failure. Read-only paths perform reads only: no provider request, token refresh, invalidation, backfill, cache write or source append. Inflight sharing requires exact subject, source, window, scope and credential compatibility. Source selection precedes overlay composition; a handle-only composed cache cannot bypass current source authorization.

Selection distinguishes observed evidence, stale fallback, unavailable, unsupported, disabled, unlinked and a read-only miss. Preserve original data-through time, window, event-kind coverage, discovery status and reasons. Complete zeros write through. Incomplete refreshes cannot overwrite a compatible complete observation as complete. A fallback is explicitly stale and retains its original context. Even identical credentials do not prove unchanged remote repository permissions or universal private visibility; recorded accessible scope is a limit on the observation.

Reuse private `scoring_v7_sources` and `scoring_v7_source_observations` for durable source evidence; do not add a Redis mirror of private events. A proposed additive migration045 may supply service-only read/append RPCs with NULL-safe owner/actor checks, current consent, exact identity/access/window/scope binding and current linked-row identity/version. The integration/foundation owner must review exact SQL and its digest before local apply. Database checks enforce trusted server assertions, not independent provider credential authentication. Store normalized dated evidence and coverage, excluding raw provider response bodies and progress URLs. Existing owner cascades remove this data on withdrawal. Token refresh results must conditionally update/delete the exact current link UUID/version; a delayed response from an old connection cannot overwrite or unlink its replacement. A proposed database-owned monotonic link timestamp makes same-millisecond updates distinct. These schema changes remain subject to exact SQL review before local apply.

Adjacent ownership includes linked-provider adapters, strict `db/user-platforms.ts` access, private coordinator/database modules and exact credential/clock propagation in the GitHub client. S15 retains public receipt materialization and scored-consumer migration. Necessary shared contract amendments return to the foundation owner rather than being introduced independently.

### Legacy compatibility during local integration

The existing v6 entrypoint serves handles that have no v7 consent record. It must not create that consent implicitly or use a legacy aggregate as a normalized source observation. During the local transition, keep a separate uncached v6 collection path with current source flags/link checks, captured credentials and detached results. Retire its unbound handle-only composed cache reads/writes and ranked in-flight reuse. Exact-context in-memory sharing may be used; private credential bindings do not become Redis keys or public data. A legacy read-only request with no safely bound stored result returns an explicit miss/null and performs no collection. The v7 coordinator remains consent-gated throughout. S15 replaces current scored consumers with the durable receipt path before relaunch; this temporary compatibility boundary is not a relaunch fallback or a waiver of missing-source disclosure.

The production Bitbucket collector must obtain canonical account identity from the authenticated current credential. It must not require the deprecated `username` response field or substitute `nickname` for a unique actor ID. Atlassian documents `account_id` and the non-unique `nickname` distinction in its [Bitbucket API privacy changes](https://developer.atlassian.com/cloud/bitbucket/bitbucket-api-changes-gdpr/). The existing OAuth profile decoder also reads `data.username`; the connected-account migration must cover the current response shape before relaunch, with a real-shape fixture. This is an additional live identity boundary to verify, not approval to drop Bitbucket or to defer supported-provider validation.

Explicit repository UUID scopes can resolve their workspace without inventing one: Atlassian documents the [empty-workspace UUID lookup](https://developer.atlassian.com/cloud/bitbucket/rest/intro/#repository-object-and-uuid). The bounded collector resolves only requested IDs, validates returned repository/workspace identities and preserves failed resolution as incomplete discovery. This uses the existing shared scope shape and collector request budget; no workspace enumeration or schema extension is necessary.

Independent review subsequently identified concurrent rotating-token refresh as a separate cross-instance race. The [refresh ownership design](2026-09-05-platform-refresh-safety.md) records the approved operational claim amendment, removal of automatic unlinking and required local proof. Exact row-version CAS alone is insufficient to coordinate provider requests.

## C: Make historical repair a grounded dry run

Retire automated `--apply` and its DELETE/DEL paths; reject it before configuration loading or I/O. Keep a dry-run inspector that binds candidate findings to exact owner/record identity, content and structured recorded evidence. Subject/window mismatch or incomplete pagination falsely labeled complete can support a finding when demonstrated. A digest, reason string, low activity or newer upload timestamp alone cannot. Legacy rows lacking such proof remain unproven. No new repair service or mutation RPC is needed, and no repair command is executed during implementation.

## Acceptance boundaries

Retain the seven root-authored policy regressions (initially six expected failures and one passing empty-profile case), then add actual-credential isolation, fallback/rotation, exact window/scope isolation, partial-page and stale-date preservation, revoked/relinked/delayed work, cold read-only behavior, ordered overlay composition, source append versus withdrawal, service-only RPC privileges and proof-bound dry-run cases. Reject `--apply` before I/O. Unsupported Bitbucket issue coverage remains visible; S08 cannot silently close S04's pending amendment.
