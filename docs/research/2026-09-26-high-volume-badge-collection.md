# High-volume badge collection and scoring: current behavior

Date: 2026-09-26
Branch examined: `develop` at `118d315c5cd4117e405e5089483cd490073a1c47`
Production examined: Chapa Supabase `main` project and public profile, 2026-09-26 09:45–10:15 Europe/Madrid

This document records the current collection, storage, scoring, and user-visible paths for accounts with tens of thousands of normalized engineering events. It records observed production behavior separately from code behavior. The repository research workflow calls for description of the existing system only.

## Entry and scheduling

- Authenticated signup, refresh, generate, reconnect, daily warm-cache, and admin paths enqueue one job per authorized provider. Enqueue is idempotent for an in-progress `(owner, provider, UTC date)` row (`apps/web/lib/collection/enqueue.ts:8-22`, `supabase/migrations/055_scoring_collection_queue.sql:79-105`, `supabase/migrations/055_scoring_collection_queue.sql:118-165`).
- A newly enqueued job receives a bounded background advance through Next.js `after()` with a default 60-second budget. The cron route calls the queue worker every five minutes with a 270-second budget and a 300-second Vercel function duration (`apps/web/lib/collection/enqueue.ts:62-92`, `apps/web/app/api/cron/collect-evidence/route.ts:7-36`, `apps/web/vercel.json:26-27`).
- The worker claims at most four jobs per batch, uses a 120-second lease, and gives each collector slice up to 150 provider requests and 60 seconds. A released job can be reclaimed within the same cron run; an expired lease can be reclaimed after a crash (`apps/web/lib/collection/worker.ts:193-202`, `apps/web/lib/collection/worker.ts:449-509`, `supabase/migrations/055_scoring_collection_queue.sql:168-194`).
- Collector checkpoints contain provider operations, cursors, discovered repository IDs, and provider-specific state. The normalized events discovered in a slice are staged separately by `(job_id, event_key)`; a key collision with different content is rejected (`apps/web/lib/collection/plan.ts:5-80`, `supabase/migrations/055_scoring_collection_queue.sql:79-105`, `supabase/migrations/057_raise_source_event_limit.sql:88-109`).
- Before each slice, the worker reads all staged event keys in 1,000-row PostgREST pages. It passes the resulting set to the collector for deduplication. A completed slice checkpoints new event bodies and then calls the finish RPC (`apps/web/lib/db/collection-queue.ts:260-284`, `apps/web/lib/collection/worker.ts:297-380`).

## Finish, storage, and scoring

- Migration 057 raised the source payload and staged-job limits from 10,000 to 50,000 normalized events. The checkpoint and finish RPCs return `event_limit` above 50,000; the source validator also rejects larger payloads. The TypeScript read schema has the same 50,000-event maximum (`supabase/migrations/057_raise_source_event_limit.sql:1-7`, `supabase/migrations/057_raise_source_event_limit.sql:48-50`, `supabase/migrations/057_raise_source_event_limit.sql:110-119`, `supabase/migrations/057_raise_source_event_limit.sql:144-155`, `apps/web/lib/db/source-context.ts:29-33`).
- `scoring_collection_finish` locks the job row, counts and orders **all** staged event rows into one `jsonb_agg`, calls `scoring_v7_append_source` with that whole array, deletes all staged rows, and marks the job `complete` in the same database transaction (`supabase/migrations/057_raise_source_event_limit.sql:134-166`).
- The append RPC validates every event in that JSON array, inserts one `scoring_v7_source_observations` row with the complete array as its `payload`, and returns the full array to the caller. The finish RPC includes that returned object in its own response (`supabase/migrations/057_raise_source_event_limit.sql:49-85`, `supabase/migrations/045_scoring_v7_source_context.sql:187-210`, `supabase/migrations/057_raise_source_event_limit.sql:156-166`).
- The source read RPC retrieves the complete stored array and validates it again. The TypeScript caller parses the full response with Zod and then loops over the events for contextual checks (`supabase/migrations/045_scoring_v7_source_context.sql:212-235`, `apps/web/lib/db/source-context.ts:33-69`, `apps/web/lib/db/source-context.ts:104-110`).
- At issuance, `collectSources` gathers all providers' event arrays into memory. The observed-receipt materializer canonicalizes the combined evidence and computes the core score from it. Issuance runs after every provider job for that owner/day is `complete`; failed issuance has a separate retry sweep (`apps/web/lib/profile/score-receipt-v7.ts:62-102`, `apps/web/lib/profile/score-receipt-observed.ts:155-201`, `apps/web/lib/collection/fan-in.ts:75-129`, `apps/web/lib/collection/fan-in.ts:143-154`).
- A new day's job can seed from the prior observation: it reads the prior full event set, filters it to the new window, and stages those bodies on the new job's first slice (`apps/web/lib/collection/worker.ts:204-233`, `apps/web/lib/collection/worker.ts:297-325`, `apps/web/lib/collection/seed.ts:18-63`).
- The runbook records a local measurement at 30,000 events of about 1.5 KB each: finish 4.7 seconds and source read-back 3.6 seconds. This measurement describes that local environment and event shape; it does not measure a 100,000-event source or production issuance (`docs/runbooks/scoring-collection-queue.md:233-240`).

## User-visible states and notification

- Status is `collecting` while no current receipt exists and jobs remain active. Once operation discovery completes, its displayed percent is `operationsDone / operationsKnown`, capped at 99 until every job reaches `complete`. A failed job changes the owner status to `action_needed` (`apps/web/lib/collection/status.ts:18-42`, `apps/web/lib/collection/status.ts:64-108`).
- The generating screen polls the owner status at 1.5-second intervals for at most 15 attempts after generate succeeds. Its fixed animation and redirect do not wait for collection completion. The share page, settings, and generating screen use the owner-only `/api/scoring/status` endpoint (`apps/web/app/generating/[handle]/GeneratingProgress.tsx:12-19`, `apps/web/app/generating/[handle]/GeneratingProgress.tsx:227-268`, `apps/web/app/api/scoring/status/route.ts:15-26`).
- The score email path fires only for a significant change with an earlier observed receipt, subject to a feature flag, an email on file, user preference, and deduplication. The fan-in path returns before calling it when no previous observed receipt exists (`apps/web/lib/collection/fan-in.ts:89-125`, `apps/web/lib/email/score-bump.ts:10-16`, `apps/web/lib/email/score-bump.ts:29-57`).

## Scope of the present evidence

- The code's 50,000-event per-source bound and whole-array read/write shape are explicit (`supabase/migrations/057_raise_source_event_limit.sql:48-50`, `supabase/migrations/057_raise_source_event_limit.sql:144-159`, `apps/web/lib/db/source-context.ts:33-69`).
- The available local measurement is 30,000 events, while the largest staged production job observed here has 17,572 events. There is no measured 40,000- or 100,000-event end-to-end receipt in this evidence (`docs/runbooks/scoring-collection-queue.md:233-240`).
- The production log proves a statement timeout in the finish RPC. It does not isolate time spent in aggregation, per-event validation, insertion, return serialization, or deletion (`supabase/migrations/057_raise_source_event_limit.sql:134-166`, `supabase/migrations/045_scoring_v7_source_context.sql:187-210`).
