# Scoring v7: verification implementation design

S14 / #1309. Implementation design approved by the integration/foundation owner after GPT-6 Astra preparation. This records the concrete scope; it does not claim implementation or validation is complete. S13 is verified and integrated locally at02a2a23b.

The token format is `v7.<revisionUUID>.<64hexHMAC>`. HMAC-SHA256 covers the complete canonical receipt's exact UTF-8 bytes. The immutable revision ID permits a content-free revocation response after consent withdrawal deletes the receipt and verification rows. Such a response states only that the revision was revoked; it cannot authenticate the submitted signature once the payload is deleted. Existing8/16/32-character legacy lookups retain their original, explicitly labeled semantics.

Issuance storage must succeed before returning a retrievable link. Issuance history, current cryptographic authentication, arithmetic replay, and source corroboration are separate claims. If a rotated or unavailable key prevents HMAC recomputation, the response cannot claim successful current cryptographic verification. A valid original link does not inspect an edited SVG. Bounded read-only submitted-payload comparison uses exact canonical bytes, not the arithmetic tolerance. Invalid private payloads are neither echoed nor logged. All v7 responses, including errors and revocations, use no-store.

Additive migration044 may introduce service-only issuance/read/withdraw-with-receipts/admin-delete-with-receipts/revocation-batch RPCs using existing tables. Issuance requires NULL-safe authenticated actor checks, current owner consent, exact persisted canonical bytes and idempotent conflict handling. Withdrawal wrappers capture revision IDs under the subject lock before existing atomic deletion. They preserve cross-owner reviewer cleanup. The root must review final SQL and its hash before any disposable database apply/reset.

Cache cleanup uses S13's opaque revision-only keys. Withdrawal and administrative deletion await cleanup and report failure honestly. The existing cron repeatedly cycles through bounded tombstone batches, including previously successful deletions, because delayed writes can recur. Tombstones retain only revision identity and revocation time. Existing raw-artifact retention covers all raw kinds; batching may bound its work without changing the retention policy or return contract.

Administrative deletion must recognize exact handle ownership in known cache namespaces. A substring scan is discovery only and cannot authorize deletion of another user's keys. Unknown matches remain untouched and produce an honest incomplete result. Logs contain counts and fixed errors rather than raw keys, private bodies or upstream HTTP response bodies.

The approved adjacent ownership includes migration044, verification constants/form, verification-only EN/ES dictionary keys, versioned verification WebMCP metadata, the existing evidence withdrawal branch, existing cron cleanup branch, a small verification cleanup helper, administrative deletion helpers and their tests. V7 never passes a receipt into a v6-only WebMCP record shape. The page uses the existing route shell, semantic design tokens and fonts; the single badge renderer is preserved.

Required acceptance includes actual disposable DB issuance/withdrawal races, complete Craft round trips, signed-field mutation failures, revoked-link behavior, bounded recurring cleanup and failures, cross-user deletion isolation, legacy compatibility, and private-content exclusion from API, RSC and logs. No remote publication, production operation or new deletion product flow is authorized.

Two adjacent corrections were approved during implementation. The S07 supplemental Redis mirror contained private records and allowed a delayed write after withdrawal. V7 supplemental reads now use authorized durable storage with a final manifest check; withdrawal retries and a bounded recurring sweep remove the retired exact namespace. This changes cache mechanics without changing aging or scoring semantics.

The actual publication-adapter/API contract exposed a numeric serialization mismatch that direct SQL tests missed: the receipt value `59.91152278612738` returned in the trend row as `59.9115227861274`. The S13 snapshot boundary now applies the existing policy's `1e-10` tolerance only to finite raw-point values inside `[0,100]`. Receipt canonical bytes, identity, date, policy, action and point/range checks remain exact. No SQL, scoring formula or policy constant changed. Targeted regressions reject mismatched identities, nonfinite/out-of-domain values and discrepancies beyond the declared tolerance.
